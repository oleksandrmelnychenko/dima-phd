# Use Academic Ontologies

Опрацьовувати наукові публікації та робочі програми в межах двох проєктних онтологій. Вважати їх незавершеними моделями контексту, а не формальними чи універсальними нормативами.

## Завантажити потрібний контекст

1. Визначити домен запиту:
   - для наукової публікації, статті, анотації, ключових слів, бібліографії, етики, гіпотези або новизни прочитати [references/publication-ontology.md](references/publication-ontology.md);
   - для робочої програми, титульної сторінки, навчального навантаження, погодження або статусу дисципліни прочитати [references/working-program-ontology.md](references/working-program-ontology.md);
   - для зіставлення онтологій або розвитку їхніх схем прочитати обидва reference-файли.
2. Не парсити жоден вихідний файл як один валідний JSON-документ. Використовувати нормалізовані reference-файли для міркування, а сирі файли — лише для перевірки походження та точних формулювань.
3. Не завантажувати нерелевантну гілку лише «про всяк випадок».

## Дотримуватися меж знань

Застосовувати такий пріоритет:

1. Пряма вказівка користувача та матеріал, який користувач явно назвав нормативним для поточного завдання.
2. Застосовний нормалізований reference цієї навички.
3. Зовнішні знання — лише після прямого дозволу користувача й з окремим маркуванням.

Не домислювати відсутні сутності, властивості, зв’язки, кардинальності, обов’язковість, стандарти або винятки. Якщо прогалина чи суперечність впливає на результат:

- назвати, що саме зафіксовано;
- позначити, що не визначено або конфліктує;
- поставити одне вузьке уточнювальне питання;
- не маскувати припущення як твердження онтології.

Коли розмежування важливе, використовувати мітки `Зафіксовано в онтології`, `Робоча інтерпретація`, `Не визначено` та `Зовнішнє доповнення`.

## Виконати завдання

1. Визначити тип артефакту:
   - відрізнити наукову публікацію загалом від наукової статті;
   - для робочої програми визначити статус дисципліни, якщо від нього залежить відповідь.
2. Побудувати мінімальну карту релевантних сутностей, властивостей і обмежень із reference-файлу.
3. Виконати запит без розширення карти незафіксованими правилами.
4. Для генерації залишати нейтральні placeholders замість вигаданих назв, кодів, дат, підписів, показників або форм контролю.
5. Для перевірки розділяти:
   - відповідність зафіксованому правилу;
   - суперечність зафіксованому правилу;
   - відсутність компонента, прямо названого обов’язковим у чернетці;
   - відсутність за невизначеної обов’язковості;
   - аспект, якого онтологія не покриває;
   - питання, що потребує уточнення.
6. Не заявляти про повну нормативну відповідність на основі цих неповних онтологій.
7. Відповідати українською за замовчуванням і зберігати канонічні українські назви сутностей. Іншу мову використовувати на прохання користувача.

## Застосувати доменні правила

### Наукова публікація

- Застосовувати перелік структурних елементів лише до наукової статті, якщо користувач не визначив інше.
- Не виводити спільний онтологічний тип для всіх значень переліку «Види публікацій»: джерело його не визначає.
- Трактувати «Гіпотезу» та «Наукову новизну» як чернеткове розширення основної моделі.
- Не прирівнювати невизначені сутності `Метод` і `Висновок` до рядків «матеріали та методи» та «висновки» без підтвердження.
- Подавати кількісні та редакційні вимоги як вимоги цієї чернетки, а не універсальні правила.

### Робоча програма

- Використовувати перший блок як `base` для всіх дисциплін — це підтверджене користувачем проєктне трактування.
- Для обов’язкової дисципліни застосовувати `base`.
- Для вибіркової дисципліни застосовувати `base + explicit elective overrides`.
- Якщо явне elective-правило конфліктує з `base`, надавати йому пріоритет лише для вибіркової дисципліни.
- Не вважати відсутність поля в elective-блоці його скасуванням.
- Якщо статус невідомий і впливає на результат, спочатку уточнити його.

## Опрацювати запит поза моделлю

Якщо запит виходить за межі обох онтологій, коротко назвати межу покриття та запропонувати один із двох варіантів:

1. продовжити лише з наданими користувачем даними;
2. отримати прямий дозвіл на зовнішнє доповнення.

Не використовувати цей skill для обмеження неакадемічних завдань, які не стосуються описаних артефактів.

## Зберегти походження

- Вважати файли `suport_info/ontology_naukova_publikatsiya.json` і `suport_info/ontology_robocha_prgrama.json` read-only джерелами.
- Не виправляти їхній синтаксис, не перейменовувати `suport_info` або `prgrama` і не нормалізувати формулювання мовчки.
- Пропозиції розвитку онтології оформлювати окремо від чинної моделі з переліком доданих, змінених і невирішених елементів.
